Error 1 — Retry formula is off-by-one at base delay. The document shows baseDelay * 2^attempt starting from attempt 1 giving ~1–2 seconds, but 1000 * 2^1 = 2000ms, not 1000ms. Correct formula: baseDelay * 2^(attempt-1) so attempt 1 = 1000ms. As written, CRITICAL notifications retry at 1s, 2s, 4s, 8s... skipping the 500ms base entirely.
Error 2 — user_preferences PRIMARY KEY uses COALESCE which is invalid DDL. PRIMARY KEY (user_id, event_category, COALESCE(event_type, '*'), channel) — PostgreSQL does not allow expressions in PRIMARY KEY declarations. The correct approach is to use a generated column or replace NULL with a sentinel value like '*' using a NOT NULL column with a default.
Error 3 — MKTX-003 urgency contradicts its channel. Market Open/Close is classified as LOW urgency but targets Push-only. Push for a LOW urgency event bypasses the logic that LOW events should prefer cheaper channels (email/in-app). Either urgency should be MEDIUM or the channel preference should include in-app as primary with push as secondary.
Error 4 — Frequency cap math is internally inconsistent. Per-category hourly cap is 3/hour. Global daily cap is 12/day. With 5 categories (TXNX, RISK, SIPX, MKTX, REGX) × 3/hour × market hours (6.25h) = theoretically 93 per day, making the 12/day global cap fire before per-category caps in any realistic scenario. The caps should be ordered: per-event-type cooldown → per-category hourly → per-channel daily → global daily. As specified, the global cap makes per-category caps unreachable.
Error 5 — REGX-005 max latency is listed as < 24hours but urgency is LOW. LOW priority events have a max retry delay of 2 hours per the retry table. A notification that fails on first attempt won't meet its 24-hour SLA because LOW priority gets only 2 retries × max 2-hour delay = 4 hours potential delay before DLQ. Either urgency should be MEDIUM (3 retries, 30 min max delay) or the 24-hour latency needs a note that it accounts for retry budget.
