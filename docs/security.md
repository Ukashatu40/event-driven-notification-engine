# Security Model

Maps spec Section A10 to what is implemented, and where it is tested.

## Authentication and roles (A10.1.A)

Three roles, **each with its own credential** — the requested role is only granted if the key presented is the one configured for
that role. (Previously any holder of the service key could ask for `role: "ADMIN"`.)

| Role | Credential env var | May |
|---|---|---|
| `ADMIN` | `ADMIN_API_KEY` | everything, incl. DLQ resolution and user-data erasure |
| `OPERATOR` | `OPERATOR_API_KEY` | read-only: analytics, DLQ, notifications, preferences; notification preview |
| `SERVICE` | `SERVICE_API_KEY` | machine-to-machine: ingest events, read/update preferences, mark notifications read |

A role whose key is empty **cannot log in at all**. Access tokens live 1 hour. Refresh tokens are **single-use with reuse
detection**: each carries a `jti` recorded in Redis and consumed atomically (`GETDEL`); replaying a used token revokes the whole
token family, so a stolen token cannot outlive the legitimate user's next refresh.

Every route is either `@Public()` or `@Roles(...)`. `tests/unit/api/rbac-policy.spec.ts` reflects over every controller and fails the
build if a route is left without a policy — the guard used to check for `@Roles` metadata that no route declared, so RBAC was not
enforced anywhere.

## Input validation (A10.1.B)

One global `ValidationPipe` (strict, unknown fields rejected) plus per-event Zod payload schemas. Failures are HTTP 422:

```json
{ "error": "VALIDATION_FAILED", "message": "Event payload validation failed",
  "details": [ { "field": "payload.shortfall_amount", "error": "must be a positive number" } ],
  "request_id": "…" }
```

Handlebars uses double-brace (HTML-escaping) everywhere; a personalised value containing template syntax is treated as data
(`template-engine.service.spec.ts`).

## Rate limiting (A10.1.C)

Sliding-window limiter backed by Redis (sorted set per client), shared by all app replicas: 100 req/min standard, 10/min for
preference updates, 1000/min for webhooks. Verified live: exactly 100 requests pass, the 101st gets 429. Fails **open** if Redis is
down (logged) — rate limiting protects availability and must not take the API down. Limits are per client IP; per-user limiting is
not implemented (see *Known gaps*).

## Secrets (A10.1.D)

Environment variables only; `.env.example` has no values; required keys are validated at startup (the app refuses to boot without
`PII_ENCRYPTION_KEY`/`PII_HASH_KEY`).

## PII (A10.2)

- **At rest:** `users.phone`/`users.email` are AES-256-GCM (`enc:v1:…`), keys from env. Uniqueness and lookup use HMAC blind indexes
  (`phoneHash`, `emailHash`) under a *separate* key. `scripts/encrypt-existing-pii.ts` backfills.
- **In flight:** the RabbitMQ message carries `user:<id>`, not the address; the delivery worker decrypts just before the provider
  call. DLQ payloads redact the recipient. Redis keys hold no PII (DND cache is keyed by user id).
- **Logs:** phones `+91XXXX1234`, emails `s***@domain`; pino redacts authorization/password/email fields.
- **Retention:** a daily job scrubs `personalisationData` and `renderedContent` after 90 days (`data-retention.job.ts`). It was a
  no-op until fixed: its `WHERE NOT (metadata … = true)` is NULL for rows with no metadata, so nothing ever matched.
- **Erasure:** `DELETE /api/v1/users/:userId/data` (ADMIN) scrubs notifications, clears the blind indexes, replaces contact details
  with encrypted placeholders.
- **Webhooks:** every provider callback is signature-verified and **fails closed** when its secret is not configured.

## Infrastructure (A10.3)

Non-root container user; Postgres TLS 1.3 (`sslmode=require`; self-signed certs generated by an init container — replace with your
CA's in production); Redis `requirepass` with `FLUSHALL`, `FLUSHDB`, `KEYS`, `DEBUG` disabled; resource limits on every service;
the live dashboard WebSocket requires an ADMIN/OPERATOR JWT and CORS is limited to `CORS_ORIGINS`.

## Consent and compliance audit (A6.1, C3.3, B2.3)

`consent_records` is append-only at the database level; WhatsApp and promotional SMS/email sends are blocked at dispatch without a
valid opt-in (`CONSENT_ENFORCEMENT`); the authorising record is stored on each notification; `GET /api/v1/compliance/audit/sms` and
`/promotional-consent` (ADMIN/OPERATOR) produce the auditor's evidence. See [consent-and-digests.md](consent-and-digests.md) and ADR-006.

## Known gaps

- Per-user (as opposed to per-IP) rate limiting.
- `docker-compose.yml` still publishes infrastructure ports to the host for development convenience.
- No device-token registry: FCM real mode addresses a message to the user id and `getAccessToken()` is a stub (mock mode works).
